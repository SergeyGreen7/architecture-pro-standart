# ADR-004: Передача депозитных ставок в кол-центры

## Контекст

После запуска рекламы ожидается рост звонков, особенно от пожилых клиентов. Операторам банка и партнёра нужны актуальные общие ставки по депозитам.

В архитектуре MVP из ADR-003 ставки уже ведутся в Deposit Service и хранятся в Deposit DB. АБС не должна получать новую онлайн-нагрузку. Система банка может работать по API, а внешняя система партнёра принимает только файлы через SFTP.

## Use Cases

| Код | Участники | Сценарий |
|---|---|---|
| UC1 | Оператор банка, система кол-центра | Оператор открывает карточку ставок и консультирует клиента по актуальным условиям. |
| UC2 | Система кол-центра, Deposit Service | Система получает общий список ставок по защищённому REST API и сохраняет последнюю успешную копию. |
| UC3 | Deposit Service, SFTP-сервер банка | После публикации ставок сервис формирует CSV-файл и размещает его на SFTP. |
| UC4 | Партнёрский кол-центр | Система партнёра скачивает файл, проверяет его и показывает ставки своим операторам. |
| UC5 | Сотрудник бэк-офиса, Deposit Service | Сотрудник публикует ставки один раз; оба кол-центра получают данные из того же справочника. |

## Функциональные требования

| Код | Требование |
|---|---|
| FR1 | Deposit Service предоставляет внутренний read-only API общих депозитных ставок. |
| FR2 | Система кол-центра банка показывает продукт, срок, валюту, диапазон суммы, ставку и дату действия. |
| FR3 | При недоступности API система банка показывает последнюю успешно загруженную версию с датой обновления. |
| FR4 | Deposit Service формирует полный CSV-файл при публикации ставок и выполняет ежедневную контрольную выгрузку. |
| FR5 | Файл содержит версию, дату формирования и только общие ставки без персональных данных. |
| FR6 | Неуспешная передача повторяется автоматически; после исчерпания попыток создаётся оповещение. |
| FR7 | Партнёр скачивает файл с SFTP и не обращается к API или внутренним системам банка. |

## Нефункциональные требования

| Код | Требование |
|---|---|
| NFR1 | API ставок доступен 99,9%; целевое время ответа — до 500 мс для 95% запросов. |
| NFR2 | Новый файл появляется на SFTP не позднее 15 минут после публикации ставок. |
| NFR3 | API использует HTTPS/TLS, SFTP — ключевую аутентификацию и ограничение сетевого доступа. |
| NFR4 | CSV имеет UTF-8, согласованную схему, уникальную версию и контрольную сумму. |
| NFR5 | Запросы API, формирование, отправка и скачивание файлов журналируются и мониторятся. |
| NFR6 | Изменения не создают прямых вызовов в АБС и используют существующие Java, MS SQL и SFTP. |

## Решение

Диаграммы показывают только компоненты, связанные с новым кейсом:

- [C4 — контекст](./rates-call-centers-context.png) ([draw.io](./rates-call-centers-context.drawio));
- [C4 — компоненты](./rates-call-centers-components.png) ([draw.io](./rates-call-centers-components.drawio)).

### Основные изменения

1. **Deposit Service** остаётся владельцем ставок. В существующее приложение добавляются:
   - read-only REST API для внутреннего кол-центра;
   - фоновая задача формирования CSV;
   - передача файла на SFTP с повторными попытками и журналом.
2. **Система кол-центра банка** получает экран ставок и локальный кэш последней версии.
3. **SFTP-сервер банка** служит защищённой точкой файлового обмена.
4. **Партнёрский кол-центр** забирает CSV по расписанию и загружает его в свою систему.

Публикация ставки — единое событие для обоих каналов. Внутренний кол-центр читает актуальную версию через API, а партнёр получает полный снимок этой же версии в файле. АБС в новый обмен не включается.

## Альтернативы

### Прямой доступ кол-центров к АБС

Отклонён: повышает нагрузку на перегруженную АБС и открывает доступ внешней системе к банковскому контуру.

### Только файлы для обоих кол-центров

Проще по числу протоколов, но сотрудники банка будут видеть обновления с задержкой. REST и кэш дают более быстрый и устойчивый интерфейс.

### Отдельный сервис распространения ставок

Может быть полезен при большом числе партнёров, но для двух получателей усложнит MVP. Экспорт остаётся модулем Deposit Service.

### Email вместо SFTP

Отклонён из-за ручной обработки, слабого контроля доставки и риска использования устаревшего вложения.

## Недостатки и риски

| Риск или ограничение | Мера |
|---|---|
| Нужно поддерживать REST и файловый канал. | Единая модель ставок и контрактные тесты для API и CSV. |
| Партнёр может временно показывать старый файл. | Версия и дата в интерфейсе партнёра, повторная отправка и оповещение. |
| Ошибка формата остановит импорт. | Версионируемая схема, тестовый файл и совместное приёмочное тестирование. |
| SFTP становится дополнительной точкой эксплуатации. | Мониторинг, резервное копирование конфигурации и инструкция восстановления. |
| Кэш банка может устареть при сбое API. | Явно показывать время обновления и предупреждение оператору. |
