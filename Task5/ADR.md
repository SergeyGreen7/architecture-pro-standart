# ADR-005: Онлайн-подача заявки на кредит

## Контекст

Банк должен принимать кредитные заявки на сайте и в интернет-банке. Если данных достаточно, клиент должен получить решение не позднее одного рабочего дня.

У банка уже есть кредитный конвейер на Camunda, система скоринга и интеграция с Бюро кредитных историй (БКИ). Обмен кредитного конвейера с АБС выполняется раз в сутки. Система скоринга перегружена в рабочие часы, поэтому нельзя рассчитывать предложения для всех клиентов без ограничения нагрузки. Новые клиенты до выдачи кредита должны пройти идентификацию в отделении.

## Use Cases

| Код | Участники | Сценарий |
|---|---|---|
| UC1 | Новый клиент, сайт | Клиент видит общие кредитные продукты, вводит контактные и паспортные данные, даёт согласие на запрос в БКИ и получает предварительное решение. |
| UC2 | Клиент банка, интернет-банк | Клиент видит доступное предодобренное предложение и подаёт короткую заявку. |
| UC3 | Клиент банка, интернет-банк | Если предодобренного предложения нет, клиент заполняет стандартную заявку, выбирает счёт зачисления и подтверждает её СМС-кодом. |
| UC4 | Кредитный конвейер, скоринг, БКИ | Конвейер проверяет заявку через существующую систему скоринга; скоринг при необходимости получает кредитную историю из БКИ. |
| UC5 | Сотрудник кредитного бэк-офиса | Сотрудник рассматривает заявки в кредитном конвейере, а предодобренные заявки получает в приоритетной очереди. |
| UC6 | Клиент, Online Credit Service | Клиент видит статус заявки и получает СМС при принятии решения или необходимости предоставить данные. |
| UC7 | Новый клиент, сотрудник отделения, АБС | После предварительного одобрения новый клиент проходит идентификацию; сотрудник продолжает оформление по сквозному ID заявки. |

## Функциональные требования

| Код | Требование |
|---|---|
| FR1 | Сайт и интернет-банк показывают актуальные кредитные продукты и условия. |
| FR2 | Сайт принимает Ф. И. О., телефон, паспортные данные, параметры кредита и согласие на запрос в БКИ. |
| FR3 | Интернет-банк показывает предодобренное предложение или стандартную форму заявки. |
| FR4 | Заявка из интернет-банка подтверждается СМС-кодом через существующий СМС-шлюз. |
| FR5 | Каждая заявка получает сквозной ID, по которому её можно продолжить онлайн, в конвейере и в отделении. |
| FR6 | Заявка сохраняется до обращения к кредитному конвейеру и повторно передаётся при временном сбое. |
| FR7 | Кредитный конвейер запускает существующий скоринг и сохраняет решение и причины ручной проверки. |
| FR8 | Статусы из конвейера доступны клиентским каналам; ключевые статусы отправляются по СМС. |
| FR9 | Предодобренные предложения рассчитываются только для целевых групп вне пиковых часов и повторно проверяются при подаче заявки. |
| FR10 | Новый клиент проходит личную идентификацию в отделении до подписания договора и выдачи средств. |

## Нефункциональные и архитектурно значимые требования

| Код | Требование |
|---|---|
| NFR1 | Online Credit Service работает 24/7 с доступностью не ниже 99,9%. |
| NFR2 | Принятая заявка не теряется при недоступности конвейера, скоринга, БКИ или АБС. |
| NFR3 | Каталог, предложения и статус отвечают не дольше 500 мс для 95% запросов; решение принимается в течение рабочего дня при достаточных данных. |
| NFR4 | Число параллельных запросов к скорингу и БКИ ограничивается; массовый предрасчёт для всех клиентов запрещён. |
| NFR5 | Персональные данные шифруются при передаче и хранении; действия и согласия клиента журналируются. |
| NFR6 | Новый сервис горизонтально масштабируется и разворачивается в основном и резервном ЦОД. |
| NFR7 | Сайт и интернет-банк не обращаются к API или БД АБС и кредитного конвейера напрямую. |
| NFR8 | Используются знакомые банку Java, REST и MS SQL; контракты API и процесс восстановления документируются. |
| NFR9 | Роли и данные кредитного направления отделены от депозитного направления. |

## Решение

Диаграммы содержат только элементы, важные для онлайн-кредитования:

- [C4 — контекст](./online-credit-context.png) ([draw.io](./online-credit-context.drawio));
- [C4 — компоненты](./online-credit-components.png) ([draw.io](./online-credit-components.drawio)).

### Основные компоненты

1. **Online Credit Service** — одно новое приложение на Java/Spring Boot. Оно предоставляет API сайту и интернет-банку, хранит заявки и предложения, передаёт заявки в конвейер в фоне и возвращает статусы.
2. **Credit DB** — MS SQL для заявок, предодобренных предложений, статусов, согласий и журнала обмена.
3. **Кредитный конвейер** — существующая Camunda-система остаётся владельцем процесса рассмотрения, очередей сотрудников и вызова скоринга.
4. **Система скоринга** — существующий Python/Flask-сервис. Она получает необходимые данные из БКИ и доступных банковских источников и возвращает результат конвейеру.
5. **СМС-шлюз** — существующий канал подтверждения заявки и уведомления клиента.
6. **АБС** — остаётся системой учёта, договора и выдачи. Существующий суточный обмен с конвейером сохраняется; клиентские каналы к АБС не подключаются.

### Основной поток

1. Сайт или интернет-банк отправляет заявку по HTTPS/REST.
2. Online Credit Service проверяет данные, назначает сквозной ID и сначала сохраняет заявку в Credit DB.
3. Фоновая задача передаёт заявку в кредитный конвейер. При ошибке выполняются ограниченные повторные попытки и создаётся оповещение.
4. Конвейер вызывает скоринг; скоринг обращается к БКИ только при наличии согласия и необходимых данных.
5. Конвейер возвращает статус и решение. Online Credit Service показывает их клиенту и отправляет СМС.
6. Для нового клиента окончательная выдача продолжается в отделении после идентификации.

Предодобренные предложения рассчитываются конвейером для ограниченных целевых групп вне пиковых часов и сохраняются в Credit DB. При фактической подаче выполняется актуальная проверка. Для решения в течение дня онлайн-заявка сразу попадает в конвейер и не ждёт суточного обмена АБС.

Отдельный брокер сообщений для этого этапа не нужен: надёжность обеспечивают сохранение заявки до отправки, идемпотентный REST-контракт и фоновая повторная передача.

## Альтернативы

### Прямое подключение сайта и интернет-банка к кредитному конвейеру

Компонентов будет меньше, но клиентские каналы станут зависеть от внутренней BPM-системы. Также не будет единого буфера, API статусов и изоляции изменений конвейера. Альтернатива отклонена.

### Реализовать кредитный процесс внутри интернет-банка

Не покрывает сайт, дублирует Camunda-процесс и увеличивает зависимость от подрядчика интернет-банка. Альтернатива отклонена.

### Kafka и набор отдельных микросервисов

Упростят дальнейшее подключение большого числа потребителей, но добавят инфраструктуру и эксплуатационные расходы. Текущая версия интернет-банка несовместима с Kafka. Для двух каналов и одного конвейера это избыточно.

### Заменить существующий кредитный конвейер

Даст полный контроль над процессом, но потребует миграции работающего Camunda-решения, интеграций и истории заявок. Это не укладывается в годовой горизонт.

### Предварительно рассчитать предложения всем клиентам

Увеличит покрытие предложениями, но создаст неприемлемую нагрузку на скоринг и БКИ. Выбран ограниченный расчёт для целевых групп.

## Ограничения и последствия

| Ограничение или риск | Последствие и мера |
|---|---|
| Обмен конвейера с АБС выполняется раз в сутки. | Предварительное решение приходит онлайн, но договор и выдача могут ожидать учётного обмена. |
| Новый клиент не идентифицирован дистанционно. | Предварительное одобрение не является выдачей; требуется визит в отделение. |
| БКИ — внешняя система с собственными лимитами и сбоями. | Ограничиваются запросы; заявка сохраняется и переводится в ожидание или ручную проверку. |
| Скоринг перегружен в рабочие часы. | Предрасчёт выполняется для целевых групп вне пика; онлайн-заявки имеют приоритет и лимит параллелизма. |
| Предодобренное предложение может устареть. | При подаче заявки выполняется повторная проверка, а предложение имеет срок действия. |
| Статус временно хранится в двух системах. | Используются сквозной ID, идемпотентность, регулярная сверка и журнал интеграции. |
| Изменение Camunda-процесса частично зависит от подрядчика. | Сначала фиксируются REST-контракты и ограниченный пилотный процесс. |
